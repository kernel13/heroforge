Seven design explorations

Each of these is a working HTML page, not a picture — resize it, tab through it, type in it. Four are of the character sheet; three are of the character list you land on before it. None of them touches web/src/.

They differ along one named axis each, so that picking one answers a question rather than picking a favourite. Each takes a position, and the positions are separable — you can adopt B's layout with A's grammar, or G's tile with F's confirm step.

The sheet · A–D

These four share the same character (Sera Valhen, Fighter 4 / Rogue 3), the same real field labels, and a skills table at a realistic width. The question underneath all four is the same: deriving the arithmetic is the product, so how should a number the application worked out look different from a number you typed?

The character list · E–G

A separate question, on a separate screen: what is a character in a list? Today it is a card with a 64px portrait, a name, a class line, a level badge and a Delete button — and with two characters on it the card is mostly empty parchment. Each of these three renders the same six characters, including the ones the current card handles worst: nothing filled in, no name, three classes, and a name too long for its box.

All three also take a position on Delete, which is independent of the tile. It is currently the widest, highest-contrast control on a card whose real purpose is to be opened.

updated_at is already on CharacterSummary and the card throws it away

The list endpoint sends it; CharacterList.tsx never reads it. "Edited 3 days ago" is the single most useful thing a list of half-finished sheets can say, it wants no API change, and Intl.RelativeTimeFormat writes it in the reader's language without a French string of its own. E and G both show it; it is adoptable on the current card as it stands.

What the research said about the sheet, and what it changed

Three agents read design-systems writing on dense forms, character sheets across a dozen games and VTTs, and licensing-safe aesthetic sources. Four findings actually changed what got built:

FindingWhat it changed
A tinted tile is the wrong marker for a derived value Because a derived <output> here deliberately goes empty when a skill has no ranks, a coloured fill leaves an empty coloured box — which reads as an unfilled input. All four mockups therefore mark derived values by removing the frame and adding a second non-colour channel (face, weight, or place). That is also what WCAG 1.4.1 asks for, and it retires the current bg-secondary tile.
Printing a total beside its components at equal weight makes people double-count Observed in playtesting of pre-printed 5e sheets. So no mockup puts total and armour 8 · shield 2 · Dex 1 on one line at one weight: A mutes them into a sentence, B folds them behind a disclosure, D draws them converging.
Tabs cost discoverability, but removing them costs more D&D Beyond's revamp replaced tabs with a one-section-at-a-time dropdown and was attacked for it; the same feedback thread blamed undifferentiated emphasis, not the parchment. So C keeps the tab removal as the deliberate risk, and A, B and D keep the strip.
Multi-column skill lists are the standard answer to forty rows Call of Cthulhu 7e fits 40+ skills in four columns as one alphabetical run, with blank repeat rows inline. C and D both run two columns; the column break must follow sorted display positions while every write stays on the stored index.

Two things worth fixing whichever sheet direction wins

The field border fails WCAG 1.4.11 today

--border: #d8c3a8 composited over the card measures about 1.47:1 against the panel face. The minimum for a non-text boundary that carries meaning — and an input's border is exactly that, it is what says "this is a field" — is 3:1. Every candidate palette failed the same way until the border was deliberately darkened; the four mockups use borders measured at 3.2:1 to 4.1:1. --muted-foreground (5.5:1) and --primary (7.4:1) already pass comfortably, so this is one token, not a repaint.

tabular-nums currently sits on an unknown font

The body face is the reader's own system sans, so font-variant-numeric: tabular-nums in styles.css does whatever that machine's default sans does — it is a silent no-op on a face without the feature. Cinzel and MedievalSharp are display faces and are not in the numeric path. If a column of forty totals is meant to line up everywhere, one numeric face has to be bundled. Confirmed to ship tabular lining figures: Source Sans 3, Lato, Noto Sans, Recursive; any monospace is tabular by construction. Read node_modules/@fontsource/<name>/LICENSE before adopting — Google Fonts is not uniformly OFL.

And it is two settings, not one. Mockup A's first build set its derived numbers in the display serif and 10 came out as IO — Hoefler Text, Iowan Old Style and Georgia all default to old-style figures, which descend below the baseline and vary in height. A column of totals needs lining-nums as well as tabular-nums. Anywhere a number is set in a serif, ask for both.

CLAUDE.md's flat-footed sentence describes something the engine does not do

The document says effective_dex_bonus is applied to armor_class, touch_ac and flat_footed_ac "alike". The engine does not: defense.py:73 is flat_footed_ac(total_ac, effective_dex) = total_ac - max(effective_dex, 0), which is the SRD rule, and the golden character pins it — test_flat_footed_removes_the_capped_bonus asserts 22 against a total of 23. So the code is right and the prose is misleading; the mockups follow the code. The invariant worth writing down is the one the max(…, 0) exists for: a character with a Dexterity penalty is no harder to hit flat-footed.

Does the sheet survive French?

All four were re-rendered with French labels and skill names — Déplacement silencieux, Neutralisation de mécanisme, Connaissance (souterrains), Résistance à la magie, Classe d'armure — because a layout that only works because "Dex" is three characters is not a layout. Three results:

  • The two-column skills table holds. This was the thing most likely to break, and it doesn't: at 1600px neither C nor D ellipsises the longest French skill name. The two-column idea — the most stealable thing in either — is not English-only. Below about 1400px the columns collapse to one, which is the same behaviour as English, just sooner.
  • B's rail holds at 19rem. Mod. de caractéristique, Classe d'armure, Jets de sauvegarde and Comment ce nombre est obtenu all stay on one line. The three-column saves strip fits Fort / Réf / Volonté.
  • One real break, now fixed in all four: a field label that is one line in English and two in French stretched its grid cell and dropped that field's input a line below its neighbours, so a row of six inputs stopped being a row. Spell resistance → Résistance à la magie and Base attack bonus → Bonus de base à l'attaque both did it. The fix is align-items:end on the field grid, so a wrapped label grows upward. Worth checking in the real sheet — fields.tsx's Row uses items-end already and is fine, but any grid added later needs the same.

Minor and not fixed: a saving throw's name and its key ability (Vigueur + CON) stack onto two lines in the narrowest plates. It is legible and it is honest about the width; worth knowing before that cell is asked to hold anything else.

Recommendation for the sheet

If only one ships: A's grammar inside B's layout. The ink-stamp-vs-ruled-blank distinction is the cheapest change with the largest effect on the thing that makes this application worth using, and the sticky rail is what turns "the sheet derives values" from a claim into something you watch happen — change Dexterity at the bottom of the skills table and armour class moves in the corner of your eye. Both keep the two-page split, so no test strategy changes.

D is the one to look at if the parchment is negotiable. Its drawn derivations are the most directly on-brief idea in the set, and its ground is two CSS gradients rather than a raster, so it costs no image and survives the PDF export as flat colour. It is also the one that might read as the wrong room for a fantasy sheet — which is precisely the thing a mockup is for.

C is the experiment, not the proposal. Two-column skills and a full-width layout are worth stealing on their own; dropping the tabs is a separate decision with a real test cost, and the evidence from D&D Beyond's revamp runs against it.

Fonts in these files

The mockups render in faces available on macOS so the typography previews honestly; each file's header comment names the shippable @fontsource equivalent. Nothing here fetches anything — no CDN, no web font, no remote image, in keeping with the deployment's same-origin rule.
